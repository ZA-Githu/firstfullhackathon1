## AI کے ساتھ Spec-Driven ترقی

AI-Native ٹیموں کی سب سے بڑی ناکامی کی موڈ بہت جلدی کوڈنگ شروع کرنا ہے۔ آپ اپنا IDE کھولتے ہیں، Claude کو چلاتے ہیں، اور prompt کرنا شروع کرتے ہیں: "مجھے ایک لاگ ان پیج بناؤ۔" AI کچھ تیار کرتا ہے۔ آپ اسے ٹویک کرتے ہیں۔ آپ کو احساس ہوتا ہے کہ auth flow غلط ہے۔ دو گھنٹے بعد آپ کے پاس ایک ورکنگ پروٹو ٹائپ ہے جو غلط مسئلہ حل کرتا ہے۔

حل **Spec-Driven ترقی** ہے — ایک کوڈ لائن لکھنے سے پہلے ایک ساختہ سپیسفکیشن میں *کیا* آپ بنا رہے ہیں اور *کیوں* کو پکڑنے کا اصول۔

### Spec-Driven ورک فلو

```
صارف کا ارادہ
    ↓
/sp.specify → spec.md  (کیا + کیوں)
    ↓
/sp.plan    → plan.md  (کیسے)
    ↓
/sp.tasks   → tasks.md (کس ترتیب میں)
    ↓
/sp.implement → code   (کرو)
```

ہر مرحلہ اگلے کو کھلاتا ہے۔ AI مسودہ تیار کرنے کو چلاتا ہے؛ انسان منظوری کو چلاتا ہے۔

### Spec کیا ہے؟

ایک سپیسفکیشن بیان کرتی ہے:
- **کون** فیچر کو سروس کرتا ہے (ترجیحات کے ساتھ صارف کی کہانیاں)
- **کیا** سسٹم کو کرنا چاہیے (فنکشنل ضروریات)
- **کب** فیچر کامیاب ہے (قبولیت کے معیار اور کامیابی کے پیمانے)
- **کیا** واضح طور پر اسکوپ سے باہر ہے (غیر اہداف)

اہم بات یہ ہے کہ spec بیان **نہیں** کرتی کہ اسے *کیسے* بنانا ہے۔ وہ پلان میں تعلق رکھتے ہیں۔

### ایک مضبوط Spec Prompt لکھنا

**کمزور ارادہ:**
```
ایک رابطہ فارم بناؤ
```

**مضبوط ارادہ:**
```
/sp.specify رابطہ صفحہ
ارادہ: کتاب کے بارے میں اپ ڈیٹس چاہنے والے زائرین کے لیے waitlist کیپچر فارم بناؤ۔
فارم نام، ای میل، اور ایک اختیاری پیغام جمع کرتا ہے۔
جمع کرنے کو localStorage میں محفوظ کرو (کوئی بیک اینڈ نہیں)۔
جمع کرنے کے بعد کامیابی کی تصدیق دکھائیں۔
کامیابی کے معیار:
- جمع کرنے سے پہلے فارم ای میل فارمیٹ کی توثیق کرتا ہے
- جمع کرنے صفحہ refresh کے بعد بھی برقرار رہتے ہیں
- فارم keyboard-accessible ہے
غیر اہداف: ای میل بھیجنا، بیک اینڈ API، تصدیق
```

### ایک اچھی Spec کی تشریح

**ترجیحات کے ساتھ صارف کی کہانیاں**
ہر کہانی آزادانہ طور پر ٹیسٹ کرنے کے قابل ہے۔ P1 (تنقیدی)، P2 (اہم)، P3 (اچھا ہے) تفویض کریں۔

**فنکشنل ضروریات**
نمبر شدہ (`FR-001`، `FR-002`...)۔ غیر مذاکراتی ضروریات کے لیے "MUST" استعمال کریں۔

**کامیابی کے معیار**
قابل پیمائش نتائج، ٹیکنالوجی سے آزاد۔

**فرضیات اور غیر اہداف**
دستاویز کریں کہ آپ نے کیا فرض کیا اور آپ نے واضح طور پر کیا خارج کیا۔

:::info انگشت نما اصول
ایک spec مکمل تب ہوتا ہے جب ایک ڈویلپر جس نے کبھی آپ سے بات نہیں کی ہو وہ دستاویز سے فیچر کو درست طریقے سے لاگو کر سکے۔
:::

### Specs AI کو بہتر کیوں بناتے ہیں

جب آپ AI کو spec دیتے ہیں جس سے عمل درآمد کرنا ہے:

1. **آؤٹ پٹ زیادہ درست ہیں** — ٹھوس قبولیت کے معیار جن کے لیے ہدف بنانا ہے
2. **آؤٹ پٹ زیادہ مستقل ہیں** — کام کرنے کے لیے دستاویز کردہ فرضیات
3. **جائزے تیز ہیں** — مخصوص، نمبر شدہ ضروریات کے خلاف AI آؤٹ پٹ کو چیک کریں

### عام Spec غلطیاں

- **بہت زیادہ عمل درآمد کی تفصیل** — اگر آپ کی spec کہتی ہے "PostgreSQL استعمال کریں،" یہ بہت مخصوص ہے
- **دھندلے کامیابی کے معیار** — "صارفین خوش ہونے چاہئیں" کامیابی کا معیار نہیں ہے
- **غیر اہداف غائب ہیں** — واضح اخراج کے بغیر، اسکوپ خاموشی سے پھیلتا ہے
- **کوئی ترجیحی ترتیب نہیں** — اگر سب کچھ P1 ہے، تو کچھ نہیں ہے
